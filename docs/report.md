## テーマ

締切に追われがちな日常を少しでも楽にする、**「次に何をやればいいか」を教えてくれるタスク管理アプリ**を作りました。

世の中にタスク管理アプリは無数にありますが、多くは「登録したタスクが並ぶだけ」で、
結局どれから手を付けるかは自分で判断しなければなりません。そこで、

- 締切が近づいたタスクの重要度を**自動的に引き上げる**
- 重要度・締切・所要時間から**取り組む順番を提案する**

という 2 点にテーマを絞りました。「登録したときは低優先度でも、締切が迫れば勝手に赤くなって
上に来てくれる」という体験を中心に据えています。

## サービスの説明

Web ブラウザで動くタスク管理アプリです。主な機能は次のとおりです。

- **タスクの登録・編集・削除・完了**：タイトル・メモ・カテゴリ・重要度・期限・所要時間を設定できる
- **カテゴリ分類**：「仕事」「勉強」などのカテゴリを色つきラベルで表示。カテゴリ自体の追加も可能
- **重要度の色分け**：低（緑）／中（青）／高（オレンジ）／最優先（赤）で一目で分かる
- **重要度の自動エスカレーション**：期限が近づくほど実効重要度を自動で引き上げる
- **やるべき順番の提案**：未完了タスクを「緊急度スコア」の高い順に自動で並べ替えて表示
- **フィルタ**：未完了／すべて／完了済みで絞り込み

## 設計の説明

### 三層アーキテクチャ

課題の指定どおり、責務を 3 層に分けて構成しました。

```
[ブラウザ / TypeScript]  ──HTTP/JSON──▶  [Express / Node.js]  ──SQL──▶  [PostgreSQL]
  プレゼンテーション層          アプリケーション層           データ永続化層
```

- **プレゼンテーション層（フロント）**：HTML / CSS / TypeScript。バンドラを使わず、
  TypeScript を 1 ファイルにコンパイルして素の DOM 操作で画面を構築。REST API を
  `fetch` で呼び出す。
- **アプリケーション層（バックエンド）**：Express による REST API。入力のバリデーション、
  DB アクセス、そして**重要度の計算ロジック**を担う。
- **データ永続化層（DB）**：PostgreSQL。`tasks` と `categories` の 2 テーブル。

### データモデル

タスクの永続化にあたり、**「ユーザーが設定した重要度」と「実際に表示する重要度」を分けた**
のが設計上の要点です。DB には `base_priority`（ユーザー設定値）だけを保存し、
締切接近で格上げされた実効重要度 `effective_priority` は**保存せず、参照するたびに
サーバ側で「今」を基準に計算**します。

こうすることで、時間が経つだけで（＝ユーザーが何もしなくても）タスクの重要度が
自然に上がっていく挙動を、データの更新なしに実現できます。

主なカラム：

| テーブル | カラム | 意味 |
| --- | --- | --- |
| tasks | base_priority | ユーザーが設定した重要度 (1〜4) |
| tasks | due_date | 期限（TIMESTAMPTZ） |
| tasks | estimated_minutes | 所要時間（分） |
| tasks | completed / completed_at | 完了フラグと完了時刻 |
| categories | name / color | カテゴリ名と色 |

### インプット / プロセス / アウトプット

- **インプット**：フォームから入力されたタスク（タイトル・重要度・期限・所要時間 …）
- **プロセス**：
  - バックエンドで入力を検証し、`base_priority` として永続化
  - 一覧取得時に、締切までの残り時間から実効重要度を計算（`effectivePriority`）
  - 実効重要度・残り時間・所要時間を合成した「緊急度スコア」を計算（`urgencyScore`）し、
    未完了タスクを降順にソート
- **アウトプット**：色分け・並べ替えされたタスク一覧。締切が迫ると自動で赤くなり上位に来る

### 重要度エスカレーションのルール

| 期限までの残り | 実効重要度の下限 |
| --- | --- |
| 1週間以内 | 中 以上 |
| 3日以内 | 高 以上 |
| 24時間以内・期限切れ | 最優先 |

※ ユーザー設定値より下がることはなく、**上げる方向にのみ**作用します。

### ログインなしの利用者分離

デプロイして誰でもアクセスできるようにすると、全員が同じ 1 つのデータベースを共有して
しまい、他人のタスクが見えてしまいます。かといってログイン機能は大掛かりです。

そこで、**ブラウザの `localStorage` にランダムな匿名 ID を 1 つだけ保存**し、すべての
API リクエストに `X-Client-Id` ヘッダとして付与する方式にしました。サーバ側は全テーブルに
`client_id` を持たせ、この ID で必ず絞り込みます。これにより「ログイン画面なし」でも
「ブラウザごとに自分だけのタスク」を実現しています（データ自体は引き続き PostgreSQL に
永続化されるため、三層構成は保たれます）。

### デプロイ

Render に `render.yaml`（Infrastructure as Code）でデプロイしました。1 つのファイルで
Web サービスと PostgreSQL をまとめて定義し、`DATABASE_URL` は DB から自動注入されます。
テーブルはサーバ起動時に `CREATE TABLE IF NOT EXISTS` で冪等に作成するため、
別途マイグレーション手順は不要にしました。
